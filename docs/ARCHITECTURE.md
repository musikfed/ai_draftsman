# PEGINELAB AI Draftsman — целевая архитектура 1.0

Версия документа: 2026-11-17. Цель: лёгкая локальная студия управляемой генерации серийного манга-комикса Karate Linux, со своими LoRA, референсами и предсказуемым каноном.

## От чего отталкиваемся

- Huananzhi X79, 48 GB DDR3, RTX 3060 12 GB, Ubuntu 24.04.
- \`/1tbdisk\` имеет примерно 808 GB свободного места, поэтому **все веса моделей, датасеты, LoRA, референсы, кадры, логи и проекты — только на этом диске**, а не на почти заполненном \`/\`.
- Комикс: 24 урока, 5 **разных последовательных** свайпов на урок, 1–3 панели на свайп, 800×1000 PNG-8 (до 256 цветов). Принципиально разделять \`slide\` и \`variant\`.
- 11 языков оболочки по \`musikfed/view_my_prj\`: ru,en,zh,de,hi,fr,fi,ko,ja,it,be. Язык комикса по умолчанию русский.
- Интерфейс http://192.168.0.100:9898 — Flask + HTML/CSS/vanilla JS, без React, без тяжелого визуального фреймворка и постоянного браузерного опроса.
- Локальная Ollama уже существует: qwen3:8b (сценарии), nomic-embed-text (векторы), qwen2.5vl:7b (необязательный анализ изображения по запросу).
- ComfyUI запускаем отдельным управляемым процессом на localhost:8188 **только по нажатию ВКЛ**. Ничего не перезапускаем в других сервисах.

## Режимы генерации и работа с вариантами

1. **Text-to-image**: рисунок по описанию, без изображений-образцов. Урок/пояс/персонажи по-прежнему закреплены каноном.
2. **Image-to-image**: новое изображение по одному выбранному образцу — изменение позы/сцены с сохранением внешности.
3. **Multi-reference**: 2–10 (фактический предел зависит от выбранного checkpoint/workflow) изображений: отдельно \`character\`, \`style\`, \`pose\`, \`environment\`, \`composition\`; для каждого роль и вес влияния. В модели SDXL нужны реальные подходящие nodes/workflow, например IP-Adapter/ControlNet. Один произвольный workflow ComfyUI НЕ умеет автоматически все режимы.
4. **Локальная LoRA**: обучаем на законных своих образцах Грепа, ROOT, слона и визуального стиля; используем с совместимым checkpoint. Даты и ограничения лицензий фиксировать в карточке модели.

Внутри одного свайпа допустимы **1–3 альтернативных варианта** изображений, если их явно заказали; они не считаются новыми слайдами. Один победивший вариант получает статус \`selected\`, остальные остаются кандидатами. Пять последовательных свайпов существуют отдельно, каждый со своим сценарием.

## Данные и память

Всё в одном SQLite без внешней базы на MVP:

- \`episodes\` (1–24; заголовок, канон, допустимый пояс, фаза)
- \`slides\` (lesson, slide 1..5, story, prompt, approval)
- \`panels\` (один, два или три кадра на слайде; диалог, действие, команда, composition)
- \`characters\` и \`character_states\` (пояс, костюм, лицо, возраст, постоянные признаки)
- \`graph_nodes\`, \`graph_edges\` (следующий урок, следующий свайп, участники, появление, причинно-следственные связи)
- \`references\` (путь файла, тип и роль, персонажи, художественный стиль, лицензия, вес, разрешение; хранение изображения на диске)
- \`variants\` (slide_id, prompt, references, seed, workflow, checkpoint, LoRA, status, image paths)
- \`rag_chunks\` (+ FTS5) — куски утверждённого канона, сюжетов, справки и истории персонажей
- \`rag_embeddings\` — float32-векторы от существующей \`nomic-embed-text\`; для небольшого набора можно считать cosine по таблице, затем при росте перейти на \`sqlite-vec\`
- \`jobs\`, \`events\` — очередь генерации и журнал.
- Скриншоты/референсы остаются реальными PNG/JPG/WEBP-файлами; текстовые embeddings сами по себе не передают картинку в графический генератор.

Граф не обязан быть Neo4j: явные связи в SQLite быстрее и легче обслуживать на одном сервере. Векторная база не обязана быть Chroma: отдельного сервера для неё не нужно. При росте датасета рекомендовано добавить \`sqlite-vec\` в тот же SQLite.

Для визуального поиска референсов в MVP делаем описания изображений + текстовые embeddings. Позже CLIP/SigLIP image embeddings для поиска по визуальному сходству. Не путать два типа поиска.

## Архитектура одного задания

1. Пользователь выбирает **урок**, **слайд**, **режим** (text2img/img2img/multi-ref), количество **вариантов** (не смешивать с 5 слайдами), подходящие референсы, LoRA и модель.
2. Детерминированный \`CanonGuard\` загружает правила: тип/внешность персонажей, пояс, тема, список разрешённых технических команд, связь с предыдущим и следующим эпизодами.
3. \`GraphRetriever\` находит соседние слайды, предыдущие события, нужные состояния персонажей, сущности и зависимости.
4. \`HybridRAG\` ищет по SQLite FTS5 + vector embeddings (nomic-embed-text) среди канона, approved dialogues, описаний образцов. Top-K контекст и source_id прикладываются к промпту.
5. \`Planner\` обращается к Qwen3 через Ollama и делает **строго структурированный JSON**: пять разных свайпов (для нового урока), каждый с 1–3 кадрами. Модель не получает право менять канон/пояс; при нарушениях JSON отклоняется и корректируется.
6. \`ArtDirector\` преобразует approved story в описание сцены и набор reference role/weight; выбирает совместимый ComfyUI API-workflow для конкретного режима и checkpoint. AI не имеет права самостоятельно выбирать новый художественный стиль без подтверждения.
7. После кнопки «Генерировать» \`ComfyManager\` запускает процесс (если пользователь предварительно включил GPU-движок) и отправляет запрос. Стабильные \`seed\`, model fingerprint и LoRA записываются в variant manifest.
8. \`Inspector\` (опционально через qwen2.5vl + правила) проверяет очевидные отклонения: пояс, количество героев, обрезанные руки, рисунок не по теме; это **подсказка для проверки**, не гарантия качества.
9. \`Letterer\` рисует **точные русские реплики и команды** поверх подготовленных пустых облаков — нельзя поручать языковой точности одной диффузионной модели.
10. \`Exporter\` сохраняет утверждённый вариант в PNG-8 800×1000, сортирует 013_01…013_05 и делает ZIP только после проверки пяти страниц.

## Учитывать реальное оборудование

- Видеопамять 12 GB: SDXL / Illustrious XL + character LoRA — основной практичный генератор; другие модели можно проверять с выгрузкой компонентов на CPU.
- 48 GB RAM: позволяет offload, но 2×Xeon DDR3 замедляет его.
- Обучение полного генератора с нуля нецелесообразно. Character/style LoRA — реалистичный путь.
- Режимы image-to-image/multi-reference требуют совместимых Comfy workflows; просто загрузить разные картинки и текст недостаточно.
- Поведение ВКЛ/ВЫКЛ: панель Flask постоянна; ComfyUI запускается и завершается отдельно, завершение блокируется при активной очереди. Существующая Ollama и другие процессы не трогаются.
- UI не делает inference. Только показывает прогресс после явного запроса пользователя.
